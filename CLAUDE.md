# Project instructions

## API client

- `frontend/src/api/generated.ts` is generated by Orval and must never be hand-edited.
  A backend DTO or controller signature change requires regenerating and committing it
  in the same change: `docker exec next-app pnpm --filter @portfolio/frontend
  spec:generate`. No build or check catches a stale client.

## Code style

- This repo's Prettier config sets `printWidth: 100`. Prettier does not wrap the
  contents of string literals, so a long string (e.g. a Swagger `description`) will
  silently exceed the line width unless broken up manually. Split long string literals
  into concatenated segments - `'first part ' + 'second part'` - with each segment kept
  under the width, rather than leaving one long unbroken line.
- Comments are the exception, not the habit. Before writing one, apply this test: does a
  reader who has the code in front of them still not know something they need? If they
  would work it out from the code itself, do not write it. Delete a comment that restates
  what the line does, that names the option sitting next to it, or that argues why a
  rejected alternative was rejected - design rationale belongs in the architecture doc,
  not repeated across every file it touched. What earns a comment is knowledge external to
  the file: a deliberate-looking typo that matches a live table, an ORM default being
  overridden, a value that diverges from the schema it was generated from, a change that
  would silently break something elsewhere. A comment that survives the test gets **two
  lines at most** - two lines, not two sentences wrapped across four.
- After any edit to backend or frontend source, run that workspace's typecheck and lint
  (e.g. `pnpm --filter @portfolio/backend typecheck && pnpm --filter @portfolio/backend
  lint`) before considering the change done. Fix real errors directly; `--fix` is fine
  for pure formatting/prettier fixes.
