# Story 9.4a: Staleness check wired into the build

Status: Done

## Context

The story the epic exists for (architecture: "9.4 adds the enforcement and is the story
the epic exists for, which is why the PRD sequences it ahead of every adoption story").
FR-21's staleness check: regenerate the OpenAPI snapshot and the frontend types from
backend source inside the two **production** Docker builds and fail if either differs
from the committed copy (D39: no CI is added; this is where the check lives instead).
Depends on stories 9.1-9.3 (the artifacts being compared must exist and be current) and
on story 9.4 (lint removal) landing first, so this story's insertion point in stage 4
`builder` is simply "after the existing `RUN pnpm --filter @portfolio/backend build`
line" with no lint line to describe around.

## Acceptance Criteria

### A. Staleness check: `backend/Dockerfile`, `builder` stage, link 1

- [x] After the existing `RUN pnpm --filter @portfolio/backend build` line in stage 4
  `builder` - the last line in that stage now that story 9.4 removed the lint step - add:
  ```dockerfile
  COPY backend/openapi.json ./backend/openapi.json
  COPY scripts ./scripts
  RUN node scripts/generate-api-contract.mjs --check --only=spec
  ```
  Invoke the script directly, not through a new root `package.json` entry - the flags
  are the content of the step.
- [x] `deploy` and `prod` stages need no edit - `deploy` is `FROM builder`, so it
  inherits both new `COPY`s automatically.
- [x] The `dev` target (stage 3, branches off `common-build` same as `builder`) is
  untouched - confirm `docker compose up` (which builds `target: ${TARGET:-dev}`) still
  works with no staleness check running, so a stale artifact never blocks the dev loop.

### B. Staleness check: `frontend/Dockerfile`, `builder` stage, link 2

- [x] In `frontend/Dockerfile`'s `builder` stage, **before** the existing
  `RUN pnpm --filter @portfolio/frontend build` line, add:
  ```dockerfile
  COPY backend/openapi.json ./backend/openapi.json
  COPY scripts ./scripts
  RUN node scripts/generate-api-contract.mjs --check --only=types
  ```
  Before `next build` so a stale contract fails in about a second instead of after a
  full Next compile.
- [x] This is the one place a `backend/` path is copied into the frontend image build
  context - it's a committed static JSON document, not backend source, and nothing in
  the frontend build imports it.
- [x] Confirm `openapi-typescript` resolves inside the frontend image with no install
  change: it's a root devDependency (story 9.2), and a filtered
  `pnpm install --filter @portfolio/frontend...` still installs the root project's own
  devDependencies. Verify by running the check inside a built `frontend` `builder`-stage
  image rather than by reading the Dockerfile (same technique story 1.6's Round 1
  verification used for the backend).
- [x] `.dockerignore` is checked and confirmed not to exclude `scripts/` or
  `backend/openapi.json` (it excludes `**/Dockerfile`, `db-dumps`, `.private`,
  `**/node_modules`, `README.md`, `**/.next`, `.git` - neither path is in that list).

### C. Verification: the failure actually fires, and names the fix

- [x] Deliberately rename one DTO field in backend source (e.g. `CoinSummaryResponseDto.holdings`
  -> `holdingsQty`) without regenerating, then run
  `TARGET=prod docker compose build` (the invocation that builds both services and
  therefore covers the full chain in one command - name this exact command in the AC
  because D39's own accounting notes no CI builds the backend image, so this is the one
  command that exercises link 1 at all). Confirm the `nest-api` image build fails at the
  new `RUN` step in `backend/Dockerfile`, with an error message naming
  `backend/openapi.json` and instructing `pnpm spec:generate` (per story 9.2's message
  format). Revert the rename.
- [x] Separately, regenerate the spec correctly (rename lands, `pnpm spec:generate` run,
  both artifacts re-committed to the working tree) but leave `frontend/types/api.d.ts`
  stale (revert only that one file). Run `docker build -f frontend/Dockerfile --target
  builder .` and confirm it fails at the `--only=types` check, independently of the
  backend image. Revert to a fully regenerated, consistent state afterward.
- [x] Confirm a failure names **one link, never the pair** - the two checks run in
  separate image builds, so a reviewer reading a single build log only ever sees one
  side. Record this as expected behavior in Dev Notes, not a defect.
- [x] With both artifacts genuinely current, `TARGET=prod docker compose build` succeeds
  end to end for both services.

## Technical Notes

- `--check` compares generated bytes against the file already on disk - it never shells
  out to `git`, because the check must run identically inside a Docker build context
  that excludes `.git` (`.dockerignore`). This was decided in story 9.2 and is not
  revisited here; this story only wires the existing `--check` flag into two Dockerfiles.
- Exact current stage layout, so the two edits land in the right place:
  `backend/Dockerfile` stages are `base` -> `deps` -> `common-build` -> `dev` -> `builder`
  -> `deploy` -> `prod`; `frontend/Dockerfile` stages are `base` -> `deps` ->
  `common-build` -> `dev` -> `builder` -> `prod`. Both Dockerfiles currently number their
  stage comments `1.`/`2.`/`2.`/`3.` inconsistently (`frontend/Dockerfile` repeats `2.`
  twice) - don't fix that numbering as part of this story, it's pre-existing and out of
  scope.
- No CI workflow exists in this repo that builds either production image
  (`.github/workflows/` has only `nginx_setup.yml` and `deployment.yml`; `deployment.yml`
  builds `frontend/Dockerfile` with no `target:`, so it goes through `builder` to `prod`
  and therefore *does* enforce link 2 on every push to `main` - but no workflow builds
  the backend image at all, so link 1 only fires locally or manually). This is expected
  and by design (D39); do not add a workflow as part of this story.

## Out of Scope

- Adding any GitHub Actions workflow (D39 - ruled out, not this story's call to revisit).
- A git pre-commit hook, a `predev`/`prebuild` script hook, or any second entry point
  into the generator (D48 - considered and rejected at the architecture level; this
  story implements the two chosen enforcement points only).
- Removing lint from `backend/Dockerfile` - story 9.4.
- Raising the two `'warn'`-level backend lint rules to `'error'` - unrelated to this
  story, which is about build-failing behavior, not rule severity.
- Any adoption of the generated types by a frontend consumer - stories 9.5/9.6.

## Dev Notes

Both checks fail independently and each names only its own artifact - AC C's third
bullet is expected behavior, not a defect: `--only=spec` runs solely inside
`backend/Dockerfile`'s `builder` stage and `--only=types` solely inside
`frontend/Dockerfile`'s `builder` stage, so a single build log can only ever surface one
side of a two-artifact staleness failure. A reviewer who sees only the frontend image
fail has no way to tell from that log alone whether the backend spec is also stale -
they'd need to build `nest-api` too, which per D39's own accounting only happens
locally/manually (no CI workflow builds it).

The deliberate-rename test used `CoinSummaryResponseDto.holdings` ->
`holdingsQty` per the AC's own example: that field is declared only in the DTO (no route
reads or writes it by name), so renaming it changes the generated OpenAPI schema without
breaking the TypeScript build - exactly the "stale contract, still-compiling code"
scenario the check exists to catch. Both artifacts were regenerated and the rename fully
reverted afterward, so the working tree carries no residual change beyond the two
Dockerfiles.
